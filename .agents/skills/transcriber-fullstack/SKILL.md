# Full-stack разработчик транскрибера и переводчика

Доводи согласованный пользовательский сценарий до реализации и проверки на обеих сторонах соединения. Контролируй сохранность разговоров, изоляцию пользователей, освобождение аудиоресурсов и понятные состояния интерфейса. Не считай существующие дефекты нормой, которую нужно сохранять.

## Подготовка задачи

- Прочитай корневой [AGENTS.md](../../../AGENTS.md), затем относящиеся к задаче разделы [карты проекта](references/project-map.md). Если репозиторий изменился, проверь пути и символы заново.
- Проверь рабочее дерево. Прочитай текущую реализацию и существующие тесты нужного сценария; README используй вместе с кодом.
- Сформулируй ожидаемое поведение и способ проверки до правок. Для небольшого исправления достаточно короткого плана; для изменения схемы, auth или жизненного цикла записи опиши также совместимость, ошибки и восстановление.
- При диагностике сверяй [исходное состояние](references/baseline.md). Это снимок исследования и предлагаемые приоритеты, а не утверждённый план работ и не автоматически воспроизведённые ошибки.

## Если меняется backend

- Различай окружения auth и transcriber: Python 3.12/Pydantic 2 и Python 3.11/заявленный Pydantic 1 соответственно. Сначала проверь реальные requirements и образы. Не объединяй зависимости вслепую.
- REST-вход валидируй схемой: тип, диапазон, пустые и неизвестные значения. Поддерживай согласованные HTTP-статусы; не маскируй сбой провайдера или сохранения под успешный ответ.
- Для пользовательских сущностей выводи `user_id` из проверенной авторизации. Проверка наличия JWT не заменяет проверку владельца. При изменении auth учитывай Bearer у профиля и query token у существующего WS/истории.
- Не смешивай sync SQLAlchemy Session с `async with`/`await`. Блокирующие DB-операции в async-пути выноси из event loop или используй согласованный async стек. Учитывай rollback, закрытие сессии и конкурентность.
- Auth использует Alembic; transcriber сейчас вызывает `create_all`. Изменение модели само по себе не обновляет существующие таблицы. Подготовь реальный путь миграции и проверку существующих данных.
- У внешних вызовов и ожиданий должны быть конечные таймауты, отмена и очистка. Повторный запрос, stop или повторная доставка события не должны удваивать сохранение и учёт использования.
- Redis содержит лимиты, кэш настроек и ещё не синхронизированные события. Продумай недоступность, восстановление, формат сериализации и согласованность с PostgreSQL. Не называй оценку аудиосекунд точным биллингом.

## Если меняется frontend

- Работай с существующими HTML/CSS и обычными скриптами. Проверяй DOM ID, порядок подключения и общие глобальные функции на всех затронутых страницах; `auth.js` используется почти везде.
- Для адресов запросов учитывай текущий origin и схему прокси. Не добавляй новые привязки к localhost. Изменение старых адресов проверь и на `/`, и на `/index.html`.
- Учитывай loading, пустой результат, отказ, истёкшую сессию, повторное нажатие и потерю сети. Ошибки должны возвращать интерфейс в управляемое состояние.
- Вставляй данные через `textContent`/DOM. Проверяй синтетические строки с HTML-разметкой в транскриптах, истории и профиле. Избегай утечки токенов в DOM, URL диагностики и консоль.
- Изменения refresh/logout проверяй на всех страницах: несколько файлов определяют собственные функции и обходят `authFetch`. Проверяй очистку access/refresh/user/settings и отсутствие бесконечных повторов.
- При изменении UI проверь узкое окно, клавиатурный доступ, подписи элементов и отсутствие PiP. Доступность захвата системного звука зависит от браузера/ОС; не обещай поддержку без проверки.

## Если меняется аудио или WebSocket

Сначала прочитай раздел аудиоконтракта в [карте](references/project-map.md). Сохраняй префикс источника, WebM/Opus и разделение потоков либо согласованно меняй клиент, сервер и проверки.

- Проверяй последовательность start → audio → interim/final → stop → done; последние данные рекордера и провайдера должны обрабатываться до завершения сохранения.
- Учитывай отказ разрешения, отсутствие аудиодорожки, WS в CONNECTING, разрыв сети, повторный start/stop и закрытие PiP. Обработчики старой сессии не должны отправлять данные в новую.
- Освобождай ресурсы при успехе, ошибке, отмене и disconnect. Общий HTTP-клиент нельзя закрывать по завершении одной сессии, если он обслуживает другие.
- Проверяй размер/тип сообщения и допустимость источника. При изменении чанков сопоставляй частоту отправки с rate limiter и пропускной способностью; не обходи лимиты для исправления потери аудио.
- В проверках изолируй провайдеры и media/WS. Для конкурентности используй минимум две независимые сессии, включая остановку одной во время работы другой.

## Проверка и сдача

Выбери относящиеся к изменению проверки из [руководства](references/verification.md). Для дефекта сначала получи воспроизведение или тест, демонстрирующий наблюдаемое нарушение. Дополняй инфраструктуру тестов по необходимости; не вводи тяжёлый набор инструментов ради одиночной проверки.

Перед сдачей просмотри diff, проверь отсутствие секретов и непреднамеренных правок, обнови затронутые ссылки/контракты. В ответе укажи результат, команды проверки, их итог и реальные ограничения. Если запуск был заблокирован окружением, не подменяй его отметкой «все тесты пройдены».
