# Проверки и запуск

Команды выполнять из корня проекта, если не указано иное. Выбирай проверки по изменению; успешная проверка синтаксиса не подтверждает API, DB или работу в браузере.

## Без внешних сервисов

```bash
git status --short
python3 .agents/skills/transcriber-fullstack/scripts/check_static.py
git diff --check
```

`check_static.py` разбирает Python через `ast.parse` без импорта приложения и `.pyc`, проверяет JS-файлы и inline JS в HTML через `node --check`, shell через `bash -n`. Нужны Python 3, Node и Bash; отсутствие инструмента или ошибка даёт ненулевой exit code. Скрипт не запускает тестовые сценарии, контейнеры, браузер, миграции или API. Он использует грамматику установленного Python, а не обеих Docker-версий.

Быстрые проверки конкретного файла:

```bash
node --check frontend/app.js
bash -n backend/services/auth/entrypoint.sh
```

Для чистой документации проверь локальные ссылки и навык системным `skill-creator/scripts/quick_validate.py`, если он доступен. Валидатор не запускает приложение и не доказывает качество инструкций.

## Проверки поведения при разработке

Новые изолированные проверки используют стандартные unittest и node:test. `npm test` и pytest не настроены. Дополняй относящиеся к изменению тесты, не запускай старые сетевые сценарии автоматически. Для Python-сервисов нужны отдельные окружения с их собственными зависимостями.

| Что меняется | Что доказать |
| --- | --- |
| REST/auth | правильные form/JSON/статусы; нет/истёкший/невалидный токен; refresh без цикла; пользователь A не читает/удаляет/скачивает данные B |
| WS/session | start/audio/final/stop/done; повторный stop; disconnect до старта и при работе; очистка после ошибки; две параллельные сессии |
| Аудио | верный source byte и WebM/Opus; финальный chunk не теряется; закрываются FFmpeg/stdin/stdout/tasks; лимиты не отбрасывают нормальный поток |
| Перевод | таймаут/ошибка/нет ключа; язык и interim/final; остановка A не закрывает клиент B; ограниченный срок/размер кэша |
| БД/Redis | нужный sync/async API, rollback и повтор; корректная сериализация; отказ и восстановление; миграция существующей схемы |
| UI | `/` и `/index.html`, прочие страницы с общим auth.js; безопасный текст; loading/error/empty; повторные клики; keyboard/узкое окно/нет PiP |

Провайдеров Deepgram/DeepL, HTTP, media и WS заменяй имитациями. Проверки миграций выполняй на отдельной временной БД; одна лишь SQLite не проверяет PostgreSQL UUID/JSON и SQL миграций.

## Живой локальный сценарий

Проводить после подготовки тестового контура и установления его допустимых побочных эффектов. Запуск auth меняет схему, shell-тесты создают пользователей. Платные вызовы и работа с реальными разговорами требуют соответствующего разрешения; ранее согласованный запуск не требует повторного подтверждения.

Перед первым запуском прочитай Compose и [известные ограничения](baseline.md). Нужны Docker/Compose, свободные порты 80/443/8000/8001/6379, env каждого сервиса, согласованная RSA-пара и TLS-сертификат. Для Google OAuth нужен корректный redirect URI; для настоящего перевода — Deepgram и DeepL. Не печатай значения окружения.

README сейчас неполон: auth `.env.example` отсутствует, TLS инструкция пишет в `certs/`, а build Nginx читает `nginx/certs/`. Не обещай чистый запуск одной командой до устранения этих расхождений. Не перегенерируй существующие ключи автоматически.

После подготовки отдельного контура:

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
curl --fail --silent --show-error https://localhost/health
curl --fail --silent --show-error https://localhost/auth/health
```

Первый запрос требует доверенного локального сертификата. Не делай отключение TLS-проверки стандартом приложения. `config --quiet` читает env, но не печатает конфигурацию; полный `docker compose config` может раскрыть секреты. `/health` сейчас не доказывает готовность всех зависимостей.

В браузере с синтетической речью/данными проверь регистрацию, вход, refresh/logout, сохранение настроек, запись каждым источником и обоими, stop/done, повторный старт, историю/скачивание/удаление, перевод, отказ разрешения и разрыв сети. Проверь отсутствие работающих tracks после остановки. Браузер/ОС/версию укажи в результате; screen audio и PiP отличаются по платформам.

## Старые тесты

- `test_full_cycle.sh` и `tests/test_full_cycle.sh` на момент обследования идентичны. Они обращаются к живому API, создают пользователя и печатают auth-ответ/токен. Не запускай их без подготовки вывода и контура. Их финальная надпись об успехе не является проверкой assertions/HTTP-ошибок.
- `tests/test_audio.py` генерирует WebM через FFmpeg и подключается к WS без актуальной авторизации и source byte.
- `tests/test_websocket.py` отправляет raw PCM вместо действующего framed WebM/Opus и тоже не передаёт JWT.
- Оба Python-сценария используют `localhost:8000`, который в Compose принадлежит auth, а не transcriber. Эти сценарии требуют обновления до использования как регрессионных тестов.

Не запускай их через слепой test discovery: это исполняемые интеграционные сценарии с возможными сетевыми и платными вызовами.

## Проверки обновлённого интерфейса

```bash
node tests/test_ui_preferences.cjs
node --test tests/frontend_ui.test.cjs
```

Первый набор проверяет предпочтения, обе локализации, синхронизацию и запоздалые ответы сервера. Второй требует установленный Chrome/Chromium (`CHROME_BIN` при нестандартном пути), поднимает loopback HTTP-сервер и отдельный временный профиль. Проверяет реальные DOM/темы/вкладки/страницы/скачивание, а API, media, WS и PiP имитирует. Снимки для проверки сохраняются в `/tmp/web-transcriber-dark.png` и `/tmp/web-transcriber-light.png`. Если sandbox запрещает loopback/Chrome, требуется разрешение среды.

В отдельных зависимостях соответствующих сервисов, без рабочего env/keys:

```bash
python -m unittest discover -s tests -p test_ui_preferences.py -v
python -m unittest discover -s tests -p test_translation_session.py -v
```

Auth-набор использует изолированные схемы/SQLite; отдельная проверка миграции005 требует TEST_POSTGRES_DSN на расходуемую PostgreSQL и работает с TEMP TABLE. На этапе реализации миграция upgrade/backfill/downgrade проверена на отдельной PostgreSQL16 tmpfs. Transcriber-набор проверяет final→persist→done, два источника/две сессии, таймаут, сбой БД и настоящий FFmpeg на синтетическом WebM. У наборов разные версии зависимостей; не запускать их в общем окружении через слепое discovery.

## Проверки Reader

```bash
node --test tests/reader_ui.test.cjs
python -m unittest discover -s tests -p test_document_import.py -v
python -m unittest discover -s tests -p test_reader_api.py -v
```

Python-наборы запускаются в зависимостях transcriber (Python3.11, включая pypdf7 и defusedxml). Импортер проверяет синтетические документы/кодировки/опасные XML и архивы. API использует isolatedSQLite и fake DeepL; опциональный TEST_POSTGRES_DSN только на расходуемую PostgreSQL проверяет сохранность старых строк, конкурентность и cascade.

Браузерный набор использует Chrome и localhost с fake Bearer API, без реальных пользователей и провайдеров. Проверяет чтение всех страниц без потерь/overflow, слово и выделение, облачко и его закрытие, место чтения и reflow, документы из истории, автосохранение/IDB после сбоя и мобайл/focus. Скриншоты проверки `/tmp/web-transcriber-reader-dark.png` и `/tmp/web-transcriber-reader-mobile.png`. Прежний frontend_ui.test.cjs остаётся регрессией аудио/тем/профиля.
