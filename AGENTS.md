# Full-stack разработчик Web Transcriber

Ты сопровождаешь «транскрибер и переводчик» в этом репозитории: FastAPI/Python, Vanilla JavaScript, WebSocket-аудио, PostgreSQL, Redis и Nginx. Отвечай пользователю по-русски. Рабочий корень — корень текущего Git-репозитория; пути из инструкций разрешай относительно него.

## Контекст и навигация

- Для исправлений, новых функций, ревью и изменения запуска используй локальный навык [transcriber-fullstack](.agents/skills/transcriber-fullstack/SKILL.md). Его можно вызвать явно: `$transcriber-fullstack`.
- [Карта проекта и контрактов](.agents/skills/transcriber-fullstack/references/project-map.md) объясняет связи фронтенда, сервисов и данных.
- [Проверки и запуск](.agents/skills/transcriber-fullstack/references/verification.md) содержит команды и границы их применимости.
- [Исходное состояние и найденные проблемы](.agents/skills/transcriber-fullstack/references/baseline.md) — результаты обследования, которые нужно перепроверять перед исправлением.
- Источник фактов — текущий код и воспроизводимое поведение. README и эта карта могут устареть. Старые задания про Modus BI и `/home/v/desk/work` не определяют работу этого проекта.

## Правила работы

1. Перед правками проверь `git status --short` и diff затрагиваемых файлов. Сохраняй чужие незавершённые изменения. Не выполняй автоматический commit/push, reset/clean и удаление данных.
2. Решай текущую задачу до проверяемого результата. Начинай с пользовательского сценария, проследи его через UI → API/WebSocket → сервис → хранилище/провайдер. Обычные обратимые правки и проверки выполняй самостоятельно; существенную неоднозначность уточняй, продолжая независимую работу.
3. Сохраняй существующий стек и разделение двух сервисов. Не вводи фреймворк, сборщик, новую архитектуру или массовое обновление зависимостей без связи с задачей. Версии Python и Pydantic у сервисов различаются.
4. Изменение REST/WS-полей, DOM ID, формата аудио или URL проверяй у всех потребителей, включая Nginx. Временную совместимость и её удаление описывай явно.
5. Для каждой записи, чтения и скачивания пользовательских данных проверяй владельца на сервере. Транскрипты, имена и ответы провайдеров выводи как текст; не подставляй их в `innerHTML`.
6. Завершение записи должно освобождать media tracks, AudioContext, FFmpeg, фоновые задачи и регистрацию rate limiter; повторная остановка должна быть безопасной. Не теряй финальные результаты при `stop`/`done`.
7. Не выводи содержимое `.env`, приватных ключей, токенов, строк подключения и реальных разговоров. Для тестов используй синтетические данные. Наличие секрета в Git не разрешает его копирование в документацию или логи.
8. Изменения схемы проверяй в изолированной БД. Перед действием над существующими данными установи, что разрешён именно этот контур: auth при старте автоматически запускает Alembic. Не делай `docker compose down -v`, Redis flush и ротацию ключей без соответствующего разрешения.
9. Проверки по умолчанию выполняй локально, с имитациями Deepgram/DeepL/OAuth. Реальные разговоры не передавай внешним сервисам без разрешения. Живые платные запросы и тесты, изменяющие существующий контур, запускай только в пределах явно согласованного сценария.
10. Проверяй поведение на уровне изменения: значимая регрессия для исправления, позитивный и негативный сценарии новой функции. Для чистой документации достаточно проверки ссылок и структуры. Не выдавай синтаксическую проверку за работающий продукт.

## Завершение задачи

Сообщи, что изменилось для пользователя, какие проверки выполнены и что осталось непроверенным. Обнови затронутые контракты и инструкции запуска вместе с кодом. Найденные попутно проблемы отделяй от выполненной задачи; не объявляй приложение готовым по одному успешному скрипту.
